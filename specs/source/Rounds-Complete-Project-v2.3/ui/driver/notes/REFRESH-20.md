## Design

The original waiting screen has a clear structure worth preserving: In review, notification expectation, four received checks and a limited Home navigation. This refresh keeps that hierarchy and the original 16:03 / four-check example.

The approved blue 24px wordmark and orange square carry forward. A pale-blue status surface with the established orange rule replaces the black/orange heading treatment. In review keeps its original 46px size with a more readable line height and the approved font weights. The short status copy is 17px.

The submitted count becomes 36px, with the explicit heading Checks received. Identity, Face check, Vehicle and Payout remain distinct. Rows grow from 58px to 72px, names from 14.5px to 18px, and check marks from 13px to 22px. Blue marks mean receipt; they do not claim approval. There are no small decorative circles or interactive-looking document controls in the waiting state.

Check status is a 68px action, kept above primary navigation. The header control is 52px. Content scrolls independently, preserving type and control sizes on short screens. Jobs and Earnings are genuinely disabled while review is pending, rather than relying on opacity and aria-disabled alone. Home and Profile remain available. No map belongs to this waiting task.

## State previews

- In review: four checks received. We’ll notify you of the result covers approval and correction requests, without implying approval is guaranteed or giving an invented turnaround time.
- Needs attention: only Identity is highlighted; the example’s Thai ID photo is unreadable. Replace ID photo opens the existing A12 `?issue=id` correction path. Other submitted checks are preserved.
- Approved: approval is explicit, while Network offers remain paused. Go to Network opens B03 `?state=off`, with no automatic availability change or redirect.
- Offline: the current decision is not presented as confirmed; status checking is disabled. The sample submission receipt remains available.
- Unconfirmed: reconnecting requires a new status check. It does not infer approval from connectivity or from the previously shown result.
- Retry: a failed refresh offers Try again without replacing the submission receipt with a false success.

Checking opens explicit local sample result choices. Closing that dialog keeps the existing state; a hidden result button cannot change it. Losing connection while checking closes the result chooser. Approval, correction or failure are never generated by a timer.

The Needs attention fixture keeps four received checks because receipt and review outcome are separate facts. The correction request does not mean the other three checks were individually approved. The Thai ID example is supported by the existing A12 issue selector; the original pending screen did not specify a failed item.
