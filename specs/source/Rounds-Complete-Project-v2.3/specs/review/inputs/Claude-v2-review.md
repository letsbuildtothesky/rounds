# Rounds Specifications v2 — Independent Re-review

Reviewer: Claude · 8 September 2026 · Package: `Rounds-Specs-v2.zip` (supersedes the v1 review of the same date)

## What was done this time

Everything in v1 was re-verified, plus two things v1 could not do. First, the reference DDL and `ROLE-POLICIES.sql` were **loaded into a real PostgreSQL 16 + PostGIS 3 instance**: `ROUNDS-REVIEW-SCHEMA.sql` applied with 0 errors (123 tables, 25 triggers); `ROLE-POLICIES.sql` applied with 4 errors, all on the Supabase-only `realtime.messages` policy (`authenticated` role absent locally — environment, not a defect), yielding 135 policies and roles `rounds_api`/`rounds_broker`. Adversarial SQL was then executed against the live database (cross-tenant reads/writes, typo states, double holds, sealed-manifest mutation, overlap exclusion, etc.). Second, `review/validate_package.py` was run and reproduces its 14 PASS lines. The contracts (979 OpenAPI components, 128 commands, 186 events, 58 state families, 56 transitions) and the review CSVs were re-measured by script. Nothing was accepted from `REVIEW-RESOLUTION.md` without checking.

## Verdict

Yes — materially better, and in the ways that matter. The v1 blockers were the right things to fix and most are actually fixed rather than relabelled: closed state families exist and match in SQL, OpenAPI and `STATE-CODES.json` (58/58, 0 mismatches); the driver-overlap exclusion now really fires for a misspelled state; tenant RLS works when attacked; single-live-hold, one-live-assignment/search/agreement/dropoff and plan-per-day constraints all raise on the live DB; sealed manifests, custody events, domain events and agreement revisions reject UPDATE/DELETE via triggers; command results are typed where it counts (`expires_at`, `upload_url`, `one_time_token`, `handoff_id`); `retained_for_review` exists end to end; transaction ownership is decided (ADR-T01); the traceability CSV is now curated (150 distinct mappings, spot-check 8/8 relevant); all 172 acceptance IDs live in their owning docs; the defaults register exists. Vague acceptance predicates dropped from 40 % to 16 %; scenarios naming an error code went from 1 to 27, containing a number from 3 to 60.

It is not build-ready yet. Of 34 v1 findings: 15 fully fixed, 17 partially, 2 open. More important are five new defects, two of which would stop a client from compiling or a dispatcher from seeing their own drivers, and one structural habit that has not changed: the product bodies were frozen and the v2 behaviour appended as "V2" sections, decisions and contracts, so P04 still does not describe the staging/inbound-dependency flow that its own acceptance cases test.

## New blockers (introduced or exposed in v2)

| ID | Where | Problem → failure | Correction |
|---|---|---|---|
| N-01 | `openapi.json` `CommitDeliveryResult` | VERIFIED. `data` is `$ref: #/CommitDeliveryResult` with `data` required — the schema references itself with no terminating shape; no finite instance validates, and a generated Dart/TS type is self-recursive. `COMMAND-CATALOG.result_schema` for CommitDelivery points at the wrapper. `validate_package.py` only runs `check_schema`, which cannot catch this. | Add `CommitDeliveryData{delivery_id, manifest_id, contact_ids[], reservation_id, delivery_reference}` and point `data` at it. Add an instance-validation step for every `*Result` to the validator. |
| N-02 | `ROLE-POLICIES.sql` `account_scope` on `drivers`, `driver_devices`, `current_positions`, `location_samples` | VERIFIED on live DB. As `rounds_api` with a dispatcher's tenant/principal context: `driver_relationships` visible = 2, `drivers` visible = 0, `current_positions` visible = 0. The policies are self-only, so the operations board cannot read a team driver's profile or live position under the API role. The only role that can is `rounds_broker` (`broker_authorized='on'`), which sees **all** tenants' drivers and tenants — and ADR-T01 scopes the broker to "conflict booleans" only. Either the board runs on the broker (tenant isolation for the most sensitive data becomes app-only) or it cannot render. Also: `notifications` is tenant-scoped only, so principal P1 can read P2's notification within the same tenant (verified, 1 row). | Add a relationship-scoped policy: `drivers` readable by `rounds_api` when `EXISTS (driver_relationships WHERE tenant_id = context_tenant() AND driver_id = drivers.id AND state active)`; same join for `current_positions`/`driver_devices` limited to active entitlement windows. Make `notifications` principal-scoped. |
| N-03 | `TRANSITIONS.json` vs `STATE-CODES.json` vs `STATE-MACHINES.md` | VERIFIED. STATE-MACHINES says "omitted transitions reject VALIDATION_FAILED". Transitions cover **18 of 58** state families (none for `stops.state`, `trip_bookings`, `trip_receipts`, `handoffs`, `driver_commitments`, …), and inside covered families 30 codes are never a `to_state`: `rounds.cancelled`, `transport_trips.cancelled`, `assignments.withdrawn/completed/received`, `plans.released/superseded`, `broadcasts.searching` (no incoming — StartBroadcast/RestartBroadcast have no row), `inbound_dependencies.discrepancy/cancelled` (P08 requires discrepancy to open), `custody_transfers.declined/cancelled/expired`, `proof_submissions.complete`. CancelTrip, CancelDelivery, PauseRound, RestartBroadcast, WithdrawChange, CancelTransfer have no transition row; one row is `"StopBroadcast\|ReviseBroadcast"` (not a command). Under the stated rule these states are unreachable. | Either complete TRANSITIONS for all 58 families (preferred — it is the artefact Codex will code from) or change the rule to "families without rows are validated by handler". Add a validator check: every non-initial code is some `to_state`; every `command` resolves. |
| N-04 | `StopView` vs `ConfirmPickupPayload.pickup_stop_id` | VERIFIED. `StopView.delivery_id` is required non-null and there is no `kind`; SQL `stops.delivery_id` is nullable with a `kind` CHECK (pickup/dropoff/return/transfer). So pickup/return/transfer stops cannot be represented in any projection and `pickup_stop_id` has no source. Two more closure gaps: `approval_decision_id` (ConfirmPickup after partial approval) exists only in an operator command result and an event, never in a projection; `handoff_id` (SubmitProof) exists only in `HandoffResultData`, and `CommandStatusProjection.result` is the generic `CommandResult` without `data`, so a driver who lost the response cannot recover it (E03 promises replay returns the original result). | `StopView{kind, delivery_id: nullable}`; `DeliveryProjection.issues[].decision_id`; `AttemptView.handoff_id`; `CommandStatusProjection.result` carries the typed `data`. Extend the validator's "journey input closure" to the full driver path. |
| N-05 | `ROLE-POLICIES.sql` L280/284, `principals` | VERIFIED. Realtime policies compare `realtime_grants.principal_id = auth.uid()`, but the auth identity column is `principals.auth_subject`; `principals.id` is a separate uuid. Unless the service forces `id = auth_subject` the policy never matches and no client can subscribe. Also `realtime_grants UNIQUE (tenant, principal, topic)` is unconditional, so re-granting after revocation raises `duplicate key` (verified); no `CHECK (expires_at > created_at)`. | Join through `principals` (`WHERE p.auth_subject = auth.uid()::text`) or document the id = auth uid invariant; partial unique `WHERE revoked_at IS NULL`. |

## What the acceptance register can now prove

Rules that had no scenario in v1 and now have a measurable one: DST ambiguous/nonexistent time (QA-SYSTEM-DST, concrete instants → `VALIDATION_FAILED`), reordered offline replay (QA-SYSTEM-OFFLINE-ORDER → `CUSTODY_MISMATCH`), partial `ReceiveReturn` (2 then 3 of 5, replay 0), changed-payload webhook (QA-ST-08 → `IDEMPOTENCY_CONFLICT`), tracking revocation (410), 1,000-driver load with thresholds (p95 400/500 ms, freshness 30 s), R0 native gate (2 h screen-off, 3 restarts, p95 ≤30 s), pre-arrival staging (QA-SYSTEM-PREARRIVAL with times and lines), last-slot race and receipt increments. Best-written cases in the set: QA-SYSTEM-PREARRIVAL, -LAST-SLOT, -RECEIPT-INCREMENTS, QA-IN-05, QA-SYSTEM-LOAD.

Still without a case: stale device `ConfirmArrival` (only `ConfirmPickup`/`SubmitProof`), tracking expiry, notification dedupe with an actual duplicate trigger, migration rollback with a defined version pair, on-road motorcycle criterion, `ApprovePartialPickup` (0 cases), any event emission.

## Readiness

Ready to start R0 (device/provider harness) and to write build specs for the own-team R1 slice **after** N-01 to N-05 and N-06 are fixed — they are each an afternoon's work in the contracts, and none needs a product decision. Do not write build specs from the P-doc bodies; write them from `decisions/`, `STATE-MACHINES`/`TRANSITIONS` (once completed to 58 families), `COMMAND-CATALOG` and the DDL, which are now the honest source of truth. The next validation step that would add real evidence is exactly what was done here: apply the DDL and policies to a real Postgres and run QA-SYSTEM-* as SQL/API tests — the package's own validator will keep passing on structural checks that cannot see N-01, N-02 or N-03.

Suggested order: N-01 (recursion) → N-02/N-05/N-12 (policies) → N-03 (transitions to 58 families + validator check) → N-04 (projection closure, validator extended to full driver path) → N-06/N-08 (error and event binding) → D-05 event/projection + ApprovePartialPickup cases → D-08/D-09/D-11 residual constraints → N-13 (decide what the P-doc bodies are for).

## Not verified

Concurrent-transaction races (template overlap, vehicle guard) — v2 delegates them to application locks, so only an API harness can test them. Supabase-specific behaviour: `realtime.messages` policy, forced disconnect on grant revocation, Supavisor transaction-mode with `SET LOCAL`. Generated Dart/TS client compilation. Grok findings F01–F29 beyond those overlapping mine. Screen/design parity (excluded by README). G-04 slot-scope precedence in handler text.
