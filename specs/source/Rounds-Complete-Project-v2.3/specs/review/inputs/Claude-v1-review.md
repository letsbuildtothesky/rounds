# Rounds Specifications Review v1 — Independent Review

Reviewer: Claude · 8 September 2026 · Package: `Rounds-Specs-Only-v1.zip`

## What was read

All 25 prose specs (product/P01–P15, engineering/E01–E10) in full. `database/ROUNDS-REVIEW-SCHEMA.sql`, `DICTIONARY.md`, `DRIVER-LOCAL-SCHEMA.sql`, `TABLE-CATALOG.json`. `contracts/COMMANDS.md`, `COMMAND-CATALOG.json`, `EVENTS.md`, `POLICY-SCHEMAS.json`; `openapi.json` and `events.json` enumerated by script and sampled (all 100 command payloads, `CommandResult`, `Error`, all 112 event schemas, all 23 queries, all 12 policy families). `review/*` fully, with the CSVs analysed by script. Every finding marked VERIFIED was confirmed against the file; nothing below relies on headings or counts.

Could not open: everything under `../foundation/` (31 of 38 relative links in the P-docs are dead in this edition) and `review/REVIEWER-GUIDE.md`, which E10 cites as the central list of proposed numeric defaults but which is not in the package. No claim is made about screen parity or legacy coverage.

## Verdict in one paragraph

These are not perfect specs, and they are not yet implementation-ready, but the skeleton is strong and the agreed product decisions are preserved everywhere (operator-owned broadcast, freelancers-only audience, manual intake primary, visible AI address review, optional Intercity, Lalamove/temperature deferred). The two real problems are structural, not local. First, the product specs are almost entirely written as prohibitions ("never", "does not", "cannot") and principles; they contain very few positive definitions — no transition tables, no command→precondition→effect→event rows, no defaults with numbers — so an implementer will have to invent the actual behaviour and the traceability will not catch it. Second, the machine contracts are half real: the 100 command *payloads*, the 12 policy schemas and the DDL table shapes are hand-specified and good, but the command *results*, the 112 events, the error contract, the read projections, the state enums and the traceability CSV are generated scaffolding that cannot be built or tested against. Fix those two things and the package becomes a genuine build basis.

## Product gaps (things the specs forgot, not defects in what is written)

| ID | Gap | Why it matters |
|---|---|---|
| G-01 | **Pickup readiness has no producer.** P04 lists "pickup readiness" as a planning input and P05 handles "pickup not ready" reactively, but no spec, command or event lets the merchant/production side declare an order ready or give a ready-by time; P02's canonical draft has no ready-at field. | For a vertically integrated tenant (kitchen/florist/production) this is the single most common planning constraint. Currently the planner plans blind and the driver discovers it. |
| G-02 | **Reschedule is one line.** `RescheduleDelivery` exists, but P05 never says whether reschedule creates a new attempt on the same delivery or a new delivery, whether it consumes a new slot unit (P03 only says a *return* doesn't reopen past admission), or how returned-to-base goods re-enter the next day's plan and who the custodian is meanwhile. | Failed-first-attempt → next-day redelivery is the most frequent exception path in gifting. |
| G-03 | **Broadcast of an already-planned team Round.** P07 lets the composer open "from a selected delivery/Round" and says starting search reserves the deliveries against team assignment; it does not say whether starting a broadcast pulls deliveries out of an existing unreleased plan, what happens to the team Round shell, or whether acceptance creates a new Round or converts the existing one. | Two competing truths on the board during the search window. |

## Acceptance-test assessment

Measured over all 121 scenarios: 0 name a tenant/driver fixture, 0 name one of the 100 commands, 0 name one of the 112 events, 1 names an error code, 3 contain a digit; 49 rest on unfalsifiable predicates ("remains", "under policy", "appropriate", "clear"). Roughly 38 are concrete, 52 need the spec section to become an assertion, 31 cannot pass or fail without inventing criteria (worst: E09-AC-26 load test "measured and accepted *or revised*"; E10-AC-28; P14-AC-04; P01-AC-04; P13-AC-05). Eight E-ACs duplicate P-ACs, so ~113 distinct scenarios. The register has no layer, environment, fixture, owner or pass criteria; `status` is one constant.

No scenario at all for: DST ambiguous/nonexistent local time (P03 demands a validation error; AC-05 is only cross-midnight); reordered offline replay (handoff before pickup) despite `command_dependencies`; a stale device issuing `ConfirmArrival`/`ConfirmPickup` on a reassigned stop; partial `ReceiveReturn`; same-provider-event-ID-with-changed-payload; tracking token revocation/expiry response; notification dedupe by event+recipient+kind; migration rollback/forward-fix; the 1,000-driver load target with a threshold; the R0 Android background-location/motorcycle field gate (E06-AC-15 only tests that the UI is honest when tracking stops). E09 names six test layers but no property/model-checked concurrency harness, no fault injection (kill worker between provider accept and ack), no offline-replay harness, no device matrix with pass thresholds, no AC→layer mapping.

## Decisions that need the product owner

1. Where transactions live (B-08): stored procedures vs TypeScript service, or a stated split.
2. Nested slot scope semantics (G-04): most-specific-wins vs both counters.
3. Pickup readiness model (G-01): merchant-declared ready state, ready-by estimate, or neither for V1.
4. Reschedule semantics (G-02): new attempt vs new delivery; whether it re-admits against slot capacity.
5. Broadcast-from-planned-Round behaviour (G-03).
6. Explicit V1 exclusions to add to P15: COD, customer fees, customer self-service changes, team-driver refusal, breaks.
7. E10's open list still stands (tariffs, retention durations, role bundles, hold TTL, proof defaults, SLOs, provider selection) and now has no home because REVIEWER-GUIDE.md is absent.
8. P14 fixes `#1754A6` blue for identity/actions and calls Dispatch Phase 39 approved; confirm this supersedes the earlier locked light theme (off-white canvas, deep navy ink, orange for attention only) or is a drift.

## What is done well

Agreed decisions are preserved without exception. Slot admission is correctly separated from vehicle capacity and return/reload, with a numbered locking algorithm (P03 is the best-written spec in the set). Custody is append-only events plus rebuildable balances; evidence is a real two-phase protocol with server-verified receipts. One-winner acceptance is enforced by `freelance_agreements UNIQUE (tenant_id, broadcast_id)` + `(tenant_id, offer_id)` and `offers UNIQUE (…, scope_revision)` with `scope_hash`, and the cross-tenant driver overlap uses a proper GiST exclusion on half-open ranges. Same-tenant composite FKs everywhere, money as integer minor units, all timestamps `timestamptz`, deferrable stop-sequence uniqueness. Command envelope and idempotency semantics are uniform and correct. The 100 payload schemas and 12 policy schemas are hand-built and precise. Deferred scope and provider gates are explicit and honest; the package never claims more than it has.

## Readiness

Not ready for implementation-ready build specs. Prose: ~80 % principle, ~20 % definition; needs transition tables, command effect tables and numeric defaults before Codex can work from it without inventing. Contracts: inputs real, outputs/events/errors/enums/projections scaffolding. Database: table shapes good, enforcement (enums, partial uniques, seal triggers, RLS policies) absent. Traceability: mechanical and non-evidential. Tests: written, largely non-falsifiable.

Order of work before build specs: B-01 → B-02/B-03/B-04 → B-05 → B-08 decision → D-01 transition tables → D-02/D-03/D-04/D-05 commands → D-06–D-09 constraints → D-10 policy bounds → B-06/B-07 register rebuild with fixtures and codes → G-01–G-08 owner decisions folded into P02–P08.
