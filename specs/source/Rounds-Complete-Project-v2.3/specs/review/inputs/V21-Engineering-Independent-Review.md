# Rounds Specifications v2.1 — Independent Re-review

Reviewer: Claude · 8 September 2026 · Package: `Rounds-Specs-v2.1.zip` · Prior: v1 and v2 reviews of the same date

## Method

Same as v2, repeated on v2.1: the DDL, `ROLE-POLICIES.sql` and `SUPABASE-REALTIME-POLICIES.sql` were applied to a fresh PostgreSQL 16 + PostGIS database (schema: 0 errors, 124 tables, 143 policies, 30 triggers, roles `rounds_api`/`rounds_broker`/`rounds_entitlements`; the Supabase file cannot apply locally — no `auth`/`realtime` schema — and was simulated). Every v2 finding (N-01–N-13 and the residual partials) was re-tested with adversarial SQL, contract scripts over the 1,505 OpenAPI components / 128 commands / 399 events / 343 transitions, and a re-measure of the 197-case register. `validate_package.py` was run (19 PASS, exit 0, confirmed read-only). File inventory vs v2: 8 added, 1 removed, 49 changed, 5 unchanged.

## Answer to "better and perfect?"

Better: yes, again, and the important things are now proven rather than claimed. On the live database a dispatcher in tenant A sees exactly the drivers related to A and nobody else; live positions are visible only inside a valid, unexpired, unrevoked time-bound grant and vanish the moment it is revoked, expired, or belongs to another tenant; a notification is readable only by its recipient; agreement revision pointers cannot be moved to another agreement or backwards; booking lines cannot mix manifests; packages under a sealed manifest are frozen; `current_manifest_id` cannot be repointed away from a sealed revision; `tenants` and `vehicle_types` are readable; vehicle shift overlap is now a real exclusion constraint; every v2 constraint and trigger still fires (22 regression checks, 22 pass). In the contracts, `CommitDeliveryResult` is finite and 527/527 examples validate with zero `$ref` cycles anywhere; all 58 state families have edges and every state is reachable; `StopView` has `kind`; the driver path closes; `GetCommandStatus` returns typed results; committed results no longer carry error fields; policy numerics are bounded for real (0 nominal maxima); required roots are explicit on 122/128 commands; obligation events and projection exist; the notification dedupe key is consistent across P09/P12/E07; P04 and P05 are rewritten as single coherent documents with the staging/inbound flow in the body; the validator is read-only and the numbers in README/E02/E03 match the files (one exception below).

Perfect: no, and it will not become perfect by another revision of this kind. Three things stand between v2.1 and "write the build specs":

1. **A handful of real defects that block a client or a flow** (five, listed first below). Each is small.
2. **The generated layer has overshot.** v2 had 186 events with 45 payload shapes; v2.1 has 399 events, of which 218 are one generated `<table>.<state>` event per transition edge, kept alongside the 120 legacy fact events for the same facts. `CompleteDelivery` now emits six events for one outcome, including `deliverie.delivered` (a singularization bug — 13 events are named `deliverie.*` / `intake_batche.*`). The 343 transition guards are 269/343 the same boilerplate sentence and, worse, are templated by target-state *name*, so the guard on `ConfirmPickup: rounds released→active` reads "receiving an invitation is not accepting a job" and the guard on creating a delivery reads "Provider outcome cannot be proved after timeout". The package's own validator passes all of this because it checks reachability and name resolution, not meaning. This layer needs pruning to one fact event per outcome and hand-written guards for the ~60 edges that matter, not expansion.
3. **The register is still two-tier.** The 25 new `QA-V21-*` cases are the best-written in the set (QA-V21-PARTIAL-APPROVAL, -RECEIPT-INDEPENDENCE, -GPS-WINDOW are exemplary). The 172 legacy cases have byte-identical `expected` text to v2: 150/172 templated steps, 0 event assertions, the same 27 codes / 60 digits / 28 vague predicates. The author acknowledges this in REVIEW-RESOLUTION; it is still the case that most features are "covered" by a case that cannot fail.

The right stopping rule is not "perfect". It is: fix the five blockers, prune the event/guard layer, and then write build specs for the R1 own-team slice from `decisions/`, `STATE-CODES`/`TRANSITIONS` (pruned), `COMMAND-CATALOG` and the DDL — and let the legacy register be upgraded per slice as each slice is built, not all at once in prose. The R0 device harness does not depend on any of this and can start now.

## Blockers (fix before build specs)

| Q-01 | `SavePolicyPayload.policy_kind` enum vs policy `kind` consts | VERIFIED. Enum has 15 values incl. `map`; `MapPolicy.kind` is `const "maps"`; `WeatherPolicy.kind` is `"weather"` and absent from the enum. E03 says `SavePolicy` validates `policy_kind == policy.kind`, so Map and Weather policies can never be saved. `policy_versions.policy_kind` has no SQL CHECK to catch it either. `WeatherPolicy` is mentioned nowhere in P13/E03/COMMANDS.md. | Align enum to 16 consts (`maps`→`map` or vice versa; add `weather`); CHECK on `policy_versions.policy_kind`; validator check that the enum equals the set of `kind` consts. |
| Q-02 | `driver_tracking_grants` (new table) | VERIFIED on live DB. The grant is what unlocks a tenant's read of `current_positions`/`location_samples`, but nothing ties `grant.driver_id` to `tracking_entitlements.driver_id`/`tenant_id` or to the round/trip/shift driver. As `rounds_entitlements` in tenant A, a grant for driver d2 (no relationship to A) pointing at **tenant B's** entitlement inserts, and A's dispatcher then reads d2's live position while `drivers` still hides d2. Also `rounds_api` has no SELECT on `tracking_entitlements` (permission denied) although the driver app must write `current_positions.tracking_entitlement_id NOT NULL` as `rounds_api`. | Composite FK `(driver_id, tracking_entitlement_id) → tracking_entitlements(driver_id, id)` and `tenant_id` match; `tracking_entitlements.tenant_id` NOT NULL; a self-scoped SELECT policy on `tracking_entitlements` for `rounds_api`. |
| Q-03 | `notifications` policy `notification_self` | VERIFIED on live DB. The fix for v2's leak made the row readable only by its recipient — and writable only by its recipient. As `rounds_api` with principal P1, inserting a notification for P2 raises RLS; `rounds_broker` has no INSERT grant. No role can fan out a notification to another principal's inbox without switching `rounds.principal_id` per row. | Split policies: SELECT/UPDATE self-only; INSERT for `rounds_api` scoped by tenant (or via the worker/broker with a tenant check). |
| Q-04 | `EVENT-CATALOG.json`, `TRANSITIONS.json`, `COMMAND-CATALOG.emitted_events` | VERIFIED. 13 events named `deliverie.*`/`intake_batche.*` (generator singularization bug) on real edges; 218 generated edge events duplicate 120 legacy fact events (`deliverie.delivered` + `delivery.completed` + `attempt.completed` + `stop.completed` + `proof.complete` + `delivery.evidence_state_complete` on one command); 70 events still carry an unbound `State_*` ref (one to the wrong family); 28 events have only a placeholder producer `worker:event_<name>`; 94/128 commands emit ≥1 event on no transition edge; envelope requires `command_id`/`actor_id` non-null on all 399 although 123 are timer/worker-produced. | Q-05 | `TRANSITIONS.json` guards, `SERVICE-ACTIONS.json` | VERIFIED. 269/343 guards start with the same sentence; 113 edges have boilerplate only; guards are chosen by target-state name (`→active`, `→received`, `→unknown`, `→failed` each get one fixed sentence regardless of domain), producing ≥25 edges whose guard contradicts the edge (TR-110, TR-140, TR-072, TR-265, TR-159, TR-234 `offered→taken` on the *winning* driver's `RespondOffer`…). 101/134 service actions share one trigger sentence; 33 exist only to name a producer. `source_events` has no command at all (six worker actions). | Hand-write guards for the edges of the eight critical operations and every edge Codex will implement in R1; delete template guards elsewhere rather than keep wrong ones; give each worker action its initiating event/timer. |
